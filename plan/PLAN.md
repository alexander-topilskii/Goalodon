# План: трекер привычек (Git as a Database)

Веб-приложение (mobile first) для трекинга привычек, задач и тренировок. Единственное хранилище — приватный GitHub-репозиторий (flat-file CMS). Этот документ — порядок работ для агента.

Модель продукта: **личный инструмент**. Новый пользователь клонирует репозиторий, запускает UI локально (или как статику), пишет данные в **свой** клон через GitHub API. Это не SaaS и не мультиарендное приложение.

---

## 0. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Пользователи | Один на клон. Чужой аккаунт не логинится в «ваш» инстанс как в облачный сервис. |
| Бэкенд | **Нет.** Нет Next.js Route Handlers, нет прокси, нет своей БД, нет Vercel serverless. GitHub API — единственный backend. |
| Фреймворк | **Vite + React + TypeScript** (не Next.js). Next.js/Auth.js требуют сервер для OAuth callback и client secret. |
| Стили | **Tailwind CSS**. |
| Авторизация | **Fine-grained PAT** (или classic PAT с `repo`), который пользователь вставляет в UI. Токен только в браузере (`sessionStorage` / `localStorage`). **NextAuth не используем.** |
| GitHub API | **`@octokit/rest`** прямо из браузера. |
| Markdown | **`gray-matter`** для YAML frontmatter + тела. |
| Данные | Каталог `/data` **в том же репозитории**, который клонировали. |
| Репозиторий | Задаётся в настройках UI (`owner/repo` + ветка `main`). Подсказка при первом запуске: вписать данные своего GitHub-клона. |
| Календарь | По умолчанию **месяц**. Можно переключиться на **год**. |
| Страница дня | Основной сценарий — **галочки**. Добавление — отдельная фича с редактором (одна или несколько задач). |
| Часовой пояс | Дата дня = **локальная** дата устройства (`YYYY-MM-DD`). |

Локаль UI: **русский**. Неделя начинается с **понедельника**.

Не делать: свой сервер, OAuth App с client secret, таймеры отдыха, офлайн-синхронизацию, публичный доступ без токена, drag-and-drop задач, полноценный WYSIWYG Markdown на весь файл.

## 1. Каркас приложения

1. `npm create vite` (React + TypeScript), Tailwind, React Router.
2. Зависимости UI: `@octokit/rest`, `gray-matter`. Без `next-auth`.
3. Маршруты:
   - `/` — календарь (месяц по умолчанию)
   - `/day/:date` — день `YYYY-MM-DD`
   - `/settings` — токен, `owner/repo`, ветка
4. Layout: mobile first, одна колонка, зоны нажатия ≥ 44px.
5. Без токена: не ходить в GitHub, показать экран настроек / онбординг.

`README`: clone → `npm i` → `npm run dev` → создать PAT → вставить в Settings → указать свой `owner/repo`.

**Готово, когда:** Vite поднимается, есть пустые календарь, день и настройки.

---

## 2. Токен и Octokit (без сервера)

GitHub OAuth Code Flow **невозможен** без сервера: нужен client secret. Поэтому вход такой:

1. Пользователь создаёт fine-grained token: Contents Read/Write на **этот** репозиторий (не весь аккаунт, если можно).
2. Вставляет токен в Settings. Кнопка «Проверить»: `octokit.repos.get({ owner, repo })`.
3. Хранение: `localStorage` (чтобы пережить reload) под ключом вроде `goalodon.token`. Не класть токен в `.env` Vite — всё `VITE_*` попадает в бандл.
4. `getOctokit()` читает токен из storage. Нет токена — нет клиента.
5. Кнопка «Выйти» только стирает токен локально.

Онбординг после клона (короткий чеклист в UI или README):

- форк/клон репозитория на GitHub (приватный);
- включить Actions;
- PAT на этот репо;
- в UI указать `owner/repo`.

**Готово, когда:** с валидным PAT читается репозиторий, с невалидным — понятная ошибка.

## 3. Контракт данных в Git

Создать канонические примеры и TypeScript-типы **до** UI.

### Дерево

```
/data
  /days
    YYYY-MM-DD.md
  graph_index.json
```

### Файл дня (`/data/days/YYYY-MM-DD.md`)

```markdown
---
date: 2026-08-19
goal: "Спроектировать структуру базы данных в Git"
---

## План
Закончить с архитектурой до обеда, вечером пойти на тренировку.

## Задачи
- [x] Греческий язык (перевод диалогов)
- [x] 1 подход: 10 чистых подтягиваний
  > Отдых 3 минуты
- [ ] 2 подход: 9 подтягиваний
  > Отдых 2 минуты
```

Правила:

- Frontmatter: `date` (`YYYY-MM-DD`), `goal` (строка).
- `## План` — свободный текст до следующей `##`.
- `## Задачи` — чеклист `- [ ]` / `- [x]`.
- Строки `  > …` сразу под задачей — напоминание, не таймер. Несколько `>` на задачу допустимы.
- Пустой день: frontmatter + пустой план + пустой список. Файл создаётся **при первом сохранении**, не при открытии.

### Индекс (`/data/graph_index.json`)

```json
{
  "generatedAt": "2026-08-19T12:00:00.000Z",
  "days": {
    "2026-08-19": {
      "goal": "Спроектировать структуру базы данных в Git",
      "total": 3,
      "done": 2,
      "hasContent": true
    }
  }
}
```

Календарь не парсит `.md`: один GET этого файла.

После сохранения дня клиент **может локально** подкрутить ячейку в памяти (`done/total`), не дожидаясь Actions. Источник правды при reload — снова индекс (возможен лаг 30–90 с).

### Модуль `lib/day-file`

- `parseDayMarkdown(raw) → DayFile`
- `serializeDayMarkdown(day) → string` (round-trip)
- Типы: `DayFile`, `DayTask { text, done, notes: string[] }`

Фикстуры (включая пример выше) + тесты round-trip.

**Готово, когда:** пример `2026-08-19.md` парсится и сериализуется без потери галочек и блоквотов.

## 4. GitHub-слой (Octokit)

| Операция | API | Заметки |
|---|---|---|
| Прочитать индекс | `GET /repos/.../contents/data/graph_index.json` | 404 → пустой календарь |
| Прочитать день | `GET .../contents/data/days/{date}.md` | Сохранить `sha` |
| Записать день | `PUT .../contents/data/days/{date}.md` | content Base64 UTF-8 + текущий `sha` |
| Создать день | тот же PUT | без `sha` |

- Ветка из настроек (`main`).
- 409 / устаревший `sha`: перечитать, показать ошибку, не затирать вслепую.
- Клиент **не** пишет `graph_index.json`.

Сообщение коммита: `chore(day): YYYY-MM-DD` (или короче). Не спамить уникальным текстом на каждый чекбокс сверх даты.

**Готово, когда:** можно прочитать и записать тестовый `.md` с PAT.

## 5. Календарь

1. Загрузка `/` — один GET `graph_index.json`.
2. **Вид по умолчанию — месяц** (сетка выбранного месяца, стрелки prev/next, подпись «август 2026»).
3. Переключение на **год**: 12 мини-месяцев или годовая сетка; тап по месяцу может вернуть в месячный вид.
4. Подсветка: нет ключа в индексе — пусто; `hasContent` — активный день; опционально плотность `done/total`.
5. Клик → `/day/YYYY-MM-DD`. Дни без файла кликабельны (пустой день в UI).
6. «Сегодня» — локальная дата устройства, ячейка выделена. Неделя с понедельника. URL месяца/года — см. §12.8.

**Готово, когда:** месяц открывается сразу, год доступен переключателем, без парсинга `/data/days`.

## 6. Страница дня (галочки + «Добавить»)

Два режима. По умолчанию пользователь **не** в редакторе.

### Режим просмотра (основной)

- Дата, **цель** и **план** — как текст (не поля ввода). Редкое редактирование: тап по цели/плану открывает компактное поле, сохранение по blur/«Готово».
- Список задач: крупные чекбоксы + текст. `>` — вторичная подпись под задачей, без таймера.
- Клик по чекбоксу — единственное частое действие: optimistic toggle + PUT.

Нет постоянного textarea на весь Markdown-файл.

### Режим «Добавить»

Кнопка **«Добавить»** открывает редактор **новых** задач (одну или несколько), не весь день.

Формат ввода — тот же чеклист, что в файле, чтобы не плодить второй язык:

```
- [ ] 3 подход: 8 подтягиваний
  > Отдых 2 минуты
- [ ] Греческий: карточки
```

Можно вставить несколько пунктов сразу. Парсер тот же, что для секции «Задачи». По «Сохранить»:

1. дописать задачи в конец списка текущего дня;
2. закрыть редактор;
3. optimistic UI + PUT.

Пустой ввод — не создавать пустых задач. Редактирование текста **уже существующих** задач в v1 не обязательно (только галочки + add). **Удаление задачи** — меню «⋯» / свайп: иначе ошибочный «Добавить» нельзя исправить. См. §12.20.

404 файла дня: пустая модель, файл появится при первой галочке или при «Добавить».

**Готово, когда:** пример из ТЗ показывается чекбоксами; «Добавить» умеет вставить одну и несколько задач с `>`.

## 7. Сохранение (Optimistic UI)

1. Клик по чекбоксу → UI сразу новый.
2. Фон: serialize → Base64 → PUT + `sha`.
3. Успех: обновить `sha` из ответа; опционально подкрутить локальную ячейку календаря.
4. Ошибка: откат + сообщение.

Очередь на файл дня: один in-flight PUT, следующие ждут новый `sha`. Текст цели/плана — debounce 300–500 ms. Чекбокс — сразу, но через ту же очередь.

**Готово, когда:** галочка мгновенная, после reload состояние то же, в Git — коммит файла дня.

## 8. GitHub Actions: выпечка `graph_index.json`

Файл `.github/workflows/build-graph.yml`.

Триггер:

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'data/days/**'
```

Коммит индекса **не** должен заново запускать workflow (путь не в `paths`).

Concurrency:

```yaml
concurrency:
  group: build-graph
  cancel-in-progress: false
```

Очередь, не отмена: частые чекбоксы не оставляют индекс от промежуточного push.

Скрипт (Node/TS, тот же `parseDayMarkdown`): все `data/days/*.md` → `data/graph_index.json`.

Коммит: `stefanzweifel/git-auto-commit-action`, `contents: write`, сообщение `chore: bake graph_index`.

В репо сразу лежат пустой `data/days/` (`.gitkeep` при необходимости) и стартовый `graph_index.json` (`generatedAt: null`, `days: {}`).

После клона пользователь **включает Actions** в своём репо (у форков они выключены по умолчанию).

**Готово, когда:** push в `data/days/**` на `main` добавляет коммит индекса.

## 11. Критерии приёмки

- Нет своего сервера и нет NextAuth. Токен только в браузере.
- Новый пользователь: clone → PAT → свой `owner/repo` → работа с `/data` его репозитория.
- Календарь открывается **месяцем**; год доступен отдельно. Данные сетки — из `graph_index.json`.
- День: обычно только чекбоксы; `>` — вторичный текст без таймеров.
- «Добавить» открывает редактор и умеет несколько задач за раз.
- Сохранение: optimistic UI + PUT (Base64 + `sha`).
- Формат дня совпадает с примером ТЗ.
- Push в `data/days/**` на `main` пересобирает индекс с concurrency `build-graph`.
- UI не читает локальный диск; без GitHub-репо и PAT календарь/день не работают.
- Round-trip не выкидывает неизвестные секции и extra frontmatter.
- Текст из `.md` не интерпретируется как HTML.
- Неделя с понедельника, UI на русском, «Сегодня», вид года = 12 мини-месяцев.

## 12. Чего не хватало в ТЗ — обязательно учесть

Ниже аспекты, без которых реализация будет хрупкой. Это не «хотелки», а дыры исходного ТЗ.

### 12.1. Клон кода ≠ локальная база

UI **никогда** не читает файлы с диска. Даже если пользователь запустил Vite из клона, все GET/PUT идут в **GitHub Contents API**.

Следствия:

- Нужен репозиторий **на GitHub** (приватный), не только папка на ноутбуке.
- Правка `.md` в IDE видна в приложении только **после push** (и индекс календаря — после Actions).
- Обратно: галочка в UI сразу на GitHub, локальный рабочий копии `git pull`, иначе IDE отстанет.
- Онбординг обязан это сказать явно, иначе «клонировал, открыл localhost, пусто / 404» выглядит как баг.

### 12.2. Онбординг (пошагово)

README + первый экран Settings, один чеклист:

1. Fork или новый приватный репозиторий с этим кодом (не public: в файлах дни и цели).
2. Если fork — **включить Actions** (у форков выключены) и разрешить Workflows писать в репо (`Settings → Actions → Workflow permissions → Read and write`).
3. Fine-grained PAT: только этот репозиторий, permission **Contents: Read and write** (Metadata Read выдаётся сам). Classic `repo` — запасной вариант, шире чем нужно.
4. Срок токена: пользователь сам; UI показывает 401 и просит вставить новый.
5. `npm i && npm run dev`, в Settings: токен, `owner/repo`, ветка (по умолчанию `main`, поле обязано быть — не у всех `main`).
6. «Проверить доступ». Успех — переход к календарю.

Без пункта про write для Actions индекс никогда не закоммитится.

### 12.3. Настройки в браузере

Схема `localStorage` (префикс `goalodon.`):

| Ключ | Что |
|---|---|
| `token` | PAT |
| `owner` | GitHub login/org |
| `repo` | имя репо |
| `branch` | ветка данных |
| `calendar` | `{ year, month, view: "month" \| "year" }` — чтобы «Назад» с дня вернуло тот же месяц |

Не хранить токен в URL, cookie, `VITE_*`, репозитории. «Выйти» чистит только `token` (owner/repo можно оставить).

Валидация: `owner/repo` — `[\w.-]+/[\w.-]+`. Пустые поля — не вызывать API.

### 12.4. Парсер: реальные файлы, не только счастливый пример

Люди будут править `.md` руками. Парсер и сериализатор должны быть заданы жёстко.

Принимать:

- чекбоксы `[ ]`, `[x]`, `[X]` (в файл писать только `[ ]` / `[x]`);
- маркеры `-` и `*` ;
- `\n` и `\r\n`;
- отсутствие `goal`, пустой `goal`, отсутствие секции `## План` или `## Задачи`;
- несколько строк `>` на одну задачу, с отступом и без;
- строки задачи без чекбокса внутри «Задачи» — как обычный текст-задача `done: false`, либо игнорировать; **выбрать одно и покрыть тестом** (предпочтение: строка `- текст` без скобок = незакрытая задача).

Не ломать:

- `date` в frontmatter расходится с именем файла → каноническое имя файла, при сохранении frontmatter привести к имени;
- в `goal` двоеточия и кавычки → YAML через безопасный dump (`gray-matter` + JSON-safe / не eval);
- неизвестные ключи frontmatter **сохранять** при round-trip;
- неизвестные секции (`## Что-то ещё`) **сохранять** как opaque-хвост, иначе ручная правка уничтожится первой галочкой.

Не парсить вложенный Markdown в текст задачи (ссылки, жирный) для UI v1: показывать как есть, одной строкой.

Битый файл: не падать всем приложением; показать «не разобрали файл», **не** автосохранять поверх (иначе порча данных в Git).

Пустой день на диск не писать: нет цели, нет плана, нет задач — PUT не делаем.

`hasContent` в индексе: `goal` или план не пустые **или** `tasks.length > 0`. Файл-скелет без текста — `hasContent: false` (лучше такой не коммитить).

### 12.5. Ключи задач и сериализация

У задачи нет id в файле. В React ключ: индекс в списке (+ текст только для отладки). Перестановка в v1 не нужна.

Сериализация всегда в канонический вид (пример ТЗ): frontmatter, пустая строка, `## План`, тело, `## Задачи`, чеклист, `  > note`. Иначе diff в Git будет шуметь пробелами.

### 12.6. Безопасность UI

Текст цели, плана, задач, `>` — **только как text** (`{task.text}`), не `dangerouslySetInnerHTML`, не markdown-to-html. Иначе XSS в `.md` + токен в `localStorage` = полный доступ к репо.

Не логировать токен, не показывать его целиком в UI после сохранения (маска `ghp_…abcd`).

CSP в `index.html` по возможности: запрет inline eval не обязателен в v1, но markdown-HTML точно нельзя.

### 12.7. GitHub API, о чём ТЗ молчит

- Contents GET отдаёт `content` + `encoding: base64`; декодировать как UTF-8 (кириллица). Не использовать `atob` без UTF-8-safe обёртки.
- Лимит файла **1 MB**. День его не должен касаться; если `truncated: true` — ошибка, не сохранить.
- Ответ PUT содержит новый `content.sha` — брать его, не делать лишний GET.
- Rate limit (~5000/ч) для одного человека ок; при 403 показать лимит, не крутить retry-шторм.
- Автор коммита = владелец PAT. Сообщение: `chore(day): YYYY-MM-DD`.
- После PUT сразу GET того же файла обычно согласован; `graph_index.json` может отставать, пока не отработает Action.
- CORS `api.github.com` для браузера с токеном работает; отдельный прокси не нужен.

Конфликты:

- **409 / sha mismatch** (вторая вкладка, правка в IDE, два устройства): стоп очереди, refetch, сообщение «день изменился, обновите», **не** авто-merge чекбоксов в v1.
- `visibilitychange` / возврат на вкладку: если есть несохранённая очередь — дописать; если очередь пуста — мягко refetch `sha`+файл, не сбрасывая галочки зря (сравнить sha).
- React Strict Mode: очередь записи должна переживать двойной mount, не слать два PUT с одним sha.

### 12.8. Календарь: UX и данные

- Локаль дат: `ru-RU`, неделя с понедельника. Дни соседнего месяца в сетке — приглушённые, кликабельные.
- Кнопка **«Сегодня»**.
- URL, чтобы не терять контекст: `/` + `?month=2026-08` или `?year=2026&view=year`. Страница дня `/day/2026-08-19`. «Назад» → тот же месяц.
- Невалидная дата в URL (`/day/2026-13-40`) — экран ошибки, не падение.
- Будущие и прошлые дни открывать можно.
- Високосный февраль, 31/30 — обычный календарь, без самописной арифметики дат (использовать `Temporal` или проверенную дату через `Date` + тесты на границах).
- Вид года на телефоне: вертикальный список 12 мини-месяцев, не одна гигантская сетка 365, которую не проскроллить к «сегодня».
- Цвет ячейки: пусто / есть контент / все задачи `done` (три состояния достаточно).
- Кнопка обновить индекс (или pull-to-refresh), потому что после галочек календарь отстаёт до CI.
- Локальный оверлей: после успешного PUT дня патчить in-memory индекс. Reload страницы снова берёт файл с GitHub (лаг допустим). Оверлей теряется при полной перезагрузке — это ок, если есть ручной refresh.

### 12.9. Навигация (mobile)

Нижняя панель из трёх точек: **Календарь** | **Сегодня** | **Настройки**. «Сегодня» всегда открывает локальную дату, даже если календарь на другом месяце.

Шапка дня: дата словами («среда, 19 августа»), не только ISO.

«Добавить» — sticky внизу над таббаром (не перекрывать системную жестовую полосу: `safe-area-inset`).

### 12.10. Редактор «Добавить»

- Отмена закрывает без записи; непустой черновик — confirm «сбросить?».
- Если пользователь ввёл строки **без** `- [ ]`, каждая непустая строка = новая задача; строки `> …` относятся к предыдущей. Иначе фича «добавить» требует помнить синтаксис.
- Строки только из пробелов — выкинуть.
- Фокус в textarea при открытии; на мобиле не зумить шрифт <16px.
- Пока открыт редактор, чекбоксы под ним лучше не трогать (оверлей/экран).

Цель и план: пустые допустимы. Плейсхолдер, не обязательные поля. Сохранять по «Готово», не на каждый символ без debounce (уже в §7).

### 12.11. Индикатор записи

Тихий статус, не модалка на каждый клик:

- очередь не пуста — точка/«сохраняем»;
- успех — ничего или «сохранено» на 1 с;
- ошибка — баннер с текстом и «повторить».

Не блокировать чекбоксы спиннером.

### 12.12. Actions-агрегатор: детали

- Скрипт: `scripts/bake-graph.ts`, **тот же** `parseDayMarkdown`, что у UI (импорт из `src/lib/...`). Запуск: `npx tsx` в workflow. Не копипастить парсер в Python.
- Node LTS в `setup-node`.
- Имя файла не `YYYY-MM-DD.md` → пропуск + warning в логе, workflow **не** падает целиком.
- Файл не парсится → пропуск этого дня, остальные пишутся.
- `git-auto-commit` не создаёт коммит, если JSON не изменился.
- Триггер только `main` (или ветка из README); если пользователь работает не с `main`, в README: либо писать в `main`, либо скопировать workflow `on.push.branches`.
- Права job: `contents: write`. `concurrency.group: build-graph`, `cancel-in-progress: false`.
- Не checkout частичный так, чтобы `data/days` обрезался: нужен полный список файлов дней (для тысяч файлов позже — ок; в v1 `fetch-depth` по умолчанию достаточен, читать с диска после checkout).

### 12.13. Два workflow в одном репо

Отдельно от выпечки индекса:

- `ci.yml` на PR/push в код приложения: `lint` + `vitest` (парсер, календарная арифметика). **Не** вызывать GitHub API в CI (нет токена пользователя).
- `build-graph.yml` не должен запускаться на изменения `src/**`, только `data/days/**`.

### 12.14. Тесты парсера (минимум фикстур)

Положить в `src/lib/day-file/fixtures/`:

1. Пример из ТЗ (кириллица, mixed done, `>`).
2. Пустой день.
3. Только цель, без задач.
4. `[X]` и `* [ ]`.
5. CRLF.
6. Extra-секция `## Заметки` — после round-trip на месте.
7. Goal со двоеточием.
8. Несколько `>` подряд.

Тест: `parse(serialize(parse(x)))` эквивалентен по модели; канонический serialize стабилен (второй serialize без диффа).

### 12.15. Доступность

- Чекбокс + текст задачи = один кликабельный ряд, имя доступности = текст задачи.
- Ячейка календаря: кнопка, `aria-label` с датой и статусом («19 августа, 2 из 3»).
- Фокус видимый; не оставлять только color для «все сделано».
- `prefers-reduced-motion`: без лишних анимаций галочки.

### 12.16. Состав репозитория

```
src/           UI
src/lib/       парсер, octokit-обёртка, storage
scripts/       bake-graph.ts
data/days/     .gitkeep
data/graph_index.json
.github/workflows/build-graph.yml
.github/workflows/ci.yml
README.md
```

`.gitignore`: `node_modules`, `dist`, `.env*`. Каталог `data/` **не** игнорировать — это база.

В корне сразу валидный пустой `graph_index.json`, иначе первый GET календаря — 404 (это тоже обработать, но файл удобнее иметь).

`README`: модель «код локально, данные на GitHub», PAT, Actions write, ветка, как открыть день руками.

### 12.17. Деплой статики (не обязателен)

Основной способ — `npm run dev` / `npm run preview` на своей машине.

GitHub Pages для **приватного** репо требует платный план; публичный Pages светит UI, но токен всё равно в браузере. В v1 **не обещать** хостинг. Если позже: `vite build` + `base: '/Goalodon/'`, SPA fallback. Серверов по-прежнему нет.

### 12.18. Производительность и лимиты v1

- Индекс: объект по датам, для нескольких лет в одном JSON ок (тысячи ключей).
- Не тянуть дерево `data/days` через `git trees` «на всякий случай».
- Год: 12 маленьких сеток, не 365 тяжёлых компонентов без виртуализации — для года хватит простых кнопок.

### 12.19. Ошибки, которые должны быть человеческими

| Ситуация | Сообщение (смысл) |
|---|---|
| Нет токена | Онбординг |
| 401 | Токен истёк, вставьте новый |
| 403 | Нет Contents Write или rate limit (различить по телу/заголовкам) |
| 404 репо | Неверный `owner/repo` или репо приватный без доступа |
| 404 дня | Норма: пустой день |
| 409 sha | «Изменено в другом месте, обновите» |
| Нет сети | «Нет сети», откат optimistic |
| Actions не пишет индекс | Календарь пустой/старый, день при этом живой; в README — write permission |

### 12.20. Сознательно не делаем, но не путать с багом

- Перенос незакрытых задач на завтра.
- Шаблоны дня / «как вчера».
- Группировка подходов в сущность «тренировка» (это просто соседние чекбоксы + `>`).
- Удаление дня, удаление задачи (v1 можно жить без delete: снять галочку нельзя убрать строку — **удаление задачи всё же стоит сделать дешёвым**: скрытая кнопка в режиме «Добавить» не покрывает удаление. Минимум v1: **свайп или «⋯» → удалить задачу**, иначе ошибочный add вечен. Если время только на одно — delete важнее правки текста.)
- PWA, офлайн-кэш, сервис-воркер.
- Тёмная тема не обязательна; система `prefers-color-scheme` — плюс, не блокер.
- Поиск по задачам, статистика стриков.

## 13. Вне скоупа первой версии

- Таймеры отдыха по тексту `> Отдых N минут`.
- Редактор всего `.md` как сырого файла.
- Правка текста уже существующих задач (delete — желателен, см. 12.20).

- Выбор репо из списка всех репозиториев аккаунта.

- Деплой на GitHub Pages / любой хостинг.
- PWA и офлайн.
- Темы оформления как отдельная работа.
